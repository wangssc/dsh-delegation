# 接外部 CLI

任何能非交互执行的命令行 AI，都能当打工人。**关键是别直接调，写一个包装层。**

---

## 为什么要包装

直接调会有五个坑，每个都让你以为「它坏了」，其实是调用方式错了。

| 坑 | 现象 | 真因 |
|---|---|---|
| 多行 prompt | 只执行第一行，或返回一句问候 | 命令行参数里的换行被 shell 吃掉 |
| 中文乱码 | 输出全是问号或方块 | Windows 控制台默认 GBK |
| 编码崩溃 | `UnicodeEncodeError: 'gbk' codec can't encode character` | 输出里有 GBK 编不出的字符 |
| 挂住不返回 | 十分钟没动静 | 工具模式在跑长任务，没设超时 |
| 模型名无效 | `400 model [xxx] is not allowed` | `--help` 列的是程序支持的，不是账号能用的 |

---

## 包装层的最小实现

```python
import json, subprocess, sys

def ask(prompt: str, files: list[str] = (), timeout: int = 180) -> str:
    """调外部 CLI。prompt 走 stdin，永不走 argv。"""
    body = prompt
    for f in files:
        body += f"\n\n===== {f} =====\n" + open(f, encoding="utf-8").read()

    r = subprocess.run(
        [CLI, "-p", "-", "--output-format", "json"],   # -p - = 从 stdin 读
        input=body,
        capture_output=True,
        text=True,
        encoding="utf-8",                              # 关键：不靠系统默认
        errors="replace",
        timeout=timeout,
    )
    # 解析结果...
```

**四条硬要求**：

1. **prompt 从 stdin 进**，不走 argv
2. **明确 `encoding="utf-8"`**，不要靠系统默认
3. **超时写死**
4. **退出码和业务失败分开**：任务跑完但输出编码崩了，退出码也是 1

## 成本对比（实测）

同一个任务，只差「给不给工具定义」：

| 模式 | 输入 token |
|---|---|
| 带工具定义 | ~23,700 |
| 只给内容、关掉工具 | **6,339** |

**差 3.7 倍。** 工具定义是固定开销，每次调用都付。

**所以**：只让它读/想/写东西时，把工具关掉。

```
--tools ""      # 大部分 CLI 都支持
```

**代价**：它不能读文件、不能跑命令。所以内容得你塞进去。

**判断法**：如果你已经把内容读进内存了，就关工具；如果要它自己去翻文件，就开着。

## 什么时候用哪种模型

| 任务 | 选什么 |
|---|---|
| 判断、短问答、格式化 | 最快最便宜的 |
| 长代码生成、重构 | 中等能力 |
| 中文写作、复杂推理 | 最强的 |

**先测成本再选**。同一个 prompt 跑两次，看 `in` / `out` 数字。

---

## 判据：什么时候值得派

**不是「难不难」，是「要读多少」。**

粗算：
- 你读 200 行 ≈ 3,000 token
- 派一次 ≈ 6,000–25,000 token（看给不给工具）

**所以界大约在 200 行**。低于这个，自己读更省。

**但如果它免费，界就低得多。** 免费的话 50 行也能派。

## 排障表

| 现象 | 查什么 |
|---|---|
| 返回一句问候 | prompt 是不是走 argv 了？改 stdin |
| 输出截断 | 是不是超了 CLI 的输出上限？加 `--raw` 看原始返回 |
| 中文乱码 | `PYTHONIOENCODING=utf-8` + `subprocess` 里写死 `encoding="utf-8"` |
| 一直不返回 | 有没有设超时？它在等交互输入吗？ |
| 说模型不存在 | 拿一个假模型名跑一次，看报错里列出哪些可用 |
| 说没权限 | 免费账号可能只开放部分模型，官网写的和实际给的不一定一样 |
| 任务做完了但退出码是 1 | 看 stderr，通常是输出阶段的编码问题，不是任务失败 |

## 一个真实的退出码教训

某次任务跑完，退出码是 1。看日志：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\xb2' in position 629
```

**崩在最后一步 `print(result)`，不是任务失败。**

如果只看退出码，会误判成「它没干成」，然后重跑一遍——重跑一次就多烧一份 token。

**所以：退出码和任务结果必须分开看。** stderr 里有堆栈时，先看堆栈。

## 让它自己检查自己

有个很便宜的技巧：**让它把验收标准当测试用例跑**。

派单里写：

```markdown
## 验收标准
1. 精确重复 3 份 → 1 组 3 文件
2. 20 个不同文件 → 误判 0 组
3. 2 个 120MB 大文件 → 能跑，不超过 5 秒
...
跑完之后，把每条的实际结果列出来。
```

它会自己造数据、自己跑、自己列结果。**你只需要核那几个数字。**

实测：让它做文件去重，它造了 761 个测试文件验证自己，跑完自己删干净，最后交了 30 个测试全过的报告。

**你要做的只是再跑一条能推翻它的检查。**
