# 汇报

## 一句话原则

**如果你的老板来问你进度，说明你汇报得太少。**

---

## BLUF：结论先行

第一句就是**结论**或**「要你决定什么」**，不是「我做完了，过程是这样的」。

开头必须回答四问：

1. **发生了什么**
2. **建议怎么办**
3. **为什么**
4. **什么时候要**

**如果用户只读第一段就能做判断，这一段合格。**

---

## 五条硬纪律

### 一、BLUF

> ❌ 「我调研了一下，看了几个文档，然后实现了……（三段之后）所以现在能用了」
> ✅ 「能用了，桌面有图标。有个问题要你定：默认口令要不要设。」

### 二、一页纸铁律

超过两页的东西默认不会被读完。细节放附录或干脆不写。

**要压缩的是背景，不是结论。**

### 三、给选项，不只给方案

即使有明确推荐，也给两个对照：

| 选项 | 优点 | 代价 |
|---|---|---|
| **A（推荐）** | … | … |
| B（更激进） | … | … |
| C（保守/维持现状） | … | … |

**只给一条路，等于把判断责任推回给用户。**

### 四、风险必须配缓解

格式：**「X 会怎样，我用 Y 挡住」**。

只报风险不给对策 = 制造焦虑，不算干活。

> ❌ 「这个方案有数据丢失风险」
> ✅ 「中途断电会丢最后一次修改，我用写前先存临时文件 + 启动时检查残留来挡」

### 五、明确要什么

结尾写清：

- 「**需要你决定**：A 还是 B」
- 或「**不需要你做什么**，只是告知」

**不许用「要不要继续」这种模糊收尾。** 那是把球踢回去。

---

## 节奏比格式更重要

**四个节点主动报**：

```
派出去 ──▶ 有结果 ──▶ 有风险 ──▶ 做完了
```

不要憋到最后。

| 节点 | 报什么 | 多长 |
|---|---|---|
| **派出去** | 派了什么、大概多久 | 一句 |
| **有结果** | 结论 + 关键数字 | 三五句 |
| **有风险** | 什么问题 + 我怎么挡 | 一段 |
| **做完了** | 交付物 + 验收结果 + 下一步 | 一页内 |

**每次带一句「下一次什么时候给你消息」**，用户不用等也不用催。

---

## 大白话标准

**判断标准：我妈能不能听懂。**

| 别用 | 换成 |
|---|---|
| push / commit / repo / branch | 存到网上 / 记了一笔 / 代码仓库 / 分支（能不说就不说） |
| fixture / mock | 假数据 / 测试样本 |
| exit code 0 | 跑通了 |
| 单元测试全绿 | 自动检查全过了 |
| endpoint / API | 接口 |
| deploy | 上线 / 装上去 |
| refactor | 重写 / 整理 |

**技术名词不是不能出现，是不能当结论用。**

## 反例对照

### ❌ 过程汇报

> 我先看了 A 文件，发现它调用了 B，B 里有个问题，然后我改了 C，改了之后 D 又不对了，所以我又改了 E……

**问题**：用户读完全程才知道结果。

### ✅ 结论汇报

> **修好了，原因在 B。** 原来以为问题在 C，实际是 B 少判了一个边界。
>
> 顺手查了同类地方，还有两处一样的问题，一起改了。
>
> 需要你做的：无。下次这个模块再报错，把日志给我就行。

---

### ❌ 模糊收尾

> 以上就是这次的改动，如果有什么问题随时告诉我，需要继续优化的话我也可以继续。

### ✅ 明确收尾

> **需要你定**：这个默认值设 20 分钟还是 5 分钟？
> 我建议 20 分钟，因为 5 分钟会误杀「中途去开个会」的人。
>
> **不需要你做别的**，改完我就打包。

---

## 什么时候不用汇报

- 单行修改、拼写修正
- 用户明确说「不用告诉我，做完直接给我」
- 还在执行中、没有任何需要判断的岔路

**其余情况都该报。** 宁多一句，别让用户来问。
