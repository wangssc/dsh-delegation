# 派单模板

## 五段，缺一不可

```
## 目标
（一句话，不要超过两行）

## 验收标准
（可执行、可验证。写不出来说明你还没想清楚）

## 边界
- 不许动：
- 不许加：
- 必须报备：

## 交付形态
（限制篇幅。「只要 20 行，不要贴日志」）

## 额外（可选，一次一条）
（顺手产出）
```

---

## 每一段怎么写

### 目标

一行说清要什么产出。**不要写怎么做。**

> ❌ 「用 zipfile 打开 docx，遍历 XML，找到 dc:creator 标签，替换成空字符串」
> ✅ 「把 Word 文件属性里的作者、标题、主题、自定义属性都清掉」

### 验收标准

**必须能被一条命令或一个动作验证。**

> ❌ 「代码要健壮」
> ❌ 「测试要充分」
> ✅ 「`normal=24 aggressive=26`，改动前后一致」
> ✅ 「不传口令时返回 HTTP 400，报错文字逐字一致」
> ✅ 「脱敏后还原，与原文逐字比对完全一致」

**写不出验收标准 = 先别派。**

### 边界

这是最容易省、也最该写的一段。

```markdown
## 边界
- 不许动：`desensitize.py` 里的 `_IDENT_RULES` 识别规则（一行都不许改）
- 不许加：任何第三方依赖（体积从 8.7 MB 涨到 15 MB 以上要单独报）
- 不许：联网
- 必须报备：如果发现需求本身有问题，先停下来说，不要自己改需求
```

**关键是给「不许」而不是「应该」。**

### 交付形态

**明说只要结论，它就不用证明自己做了多少。**

```markdown
## 交付形态
- 一段话总结改了什么
- 一张表：每条验收标准的实际结果
- 不要贴代码，不要贴日志
- 如果打断了旧用法，列出来
```

**不限篇幅时它会贴 800 行日志**——不是因为它想炫，是因为它想证明自己干了活。

### 额外

```markdown
## 额外
顺手把这次跑测试的耗时记下来，写到 README 的性能一节。
```

## 完整例子

```markdown
## 目标
给文档脱敏工具加「反向还原」：脱敏后的文本发给 AI，AI 回复粘回来，一键换回真名。

## 验收标准
1. `POST /api/restore` 传 `{"text","mapfile","password"}`，返回 `{"ok","text","replaced","unknown"}`
2. 容错：`[人员1]` `[人员 1]` `[ 人员1 ]` 三种写法都要能还原
3. 未知占位符原样保留，并出现在 `unknown` 列表里，绝不猜
4. 口令错 → 400 + `{"ok":false,"error":"口令不对"}`
5. 复制脱敏文本时自动附带提示词：「方括号加编号是占位符，原样保留，不要改写」
6. 自动复核：用映射表真值回搜脱敏文本，命中则红字列出并禁用复制按钮

## 边界
- 不许动：识别规则（`_IDENT_RULES` 及其调用链）一行都不许改
- 不许加：任何第三方依赖
- 不许：联网
- 必须报备：如果发现接口设计有问题，先停下来说
- 一句话底线：**如果还原错了，用户会把错误信息写进正式报告发给客户。宁可报「我不认识」，也不要猜。**

## 交付形态
- 改了哪几个文件，各多少行
- 每条验收标准的实际输出（贴关键几行，不要全量）
- 会打断哪些旧用法
- 不要贴完整 diff

## 额外
顺手把 `/api/restore` 的请求体例子写进 README。
```

## 常见错误

| 错误 | 后果 |
|---|---|
| 没有验收标准 | 它交付了什么你没法判对错 |
| 验收标准是「做好一点」 | 它只能猜你的标准，通常猜偏 |
| 写了实现步骤 | 它变成打字员，你的判断没被放大 |
| 没写边界 | 它顺手改了不该改的地方 |
| 不限篇幅 | 它贴一堆日志，你读的成本超过自己干 |
| 塞三条额外任务 | 主线质量掉 |

## 它报「与信里不一致」时

**优先看，先假定它是对的。**

它没有你的上下文，**正因为如此，它看到的是信里没写但实际存在的问题。**

实测三次：

1. **规格自相矛盾**：我的示例是平铺 JSON，正文却要求 `ok()` 包装。它做了包装并指出矛盾——**是我写错了。**
2. **规格与旧测试冲突**：新需求要求删掉某段配置，但旧验收脚本要求那段配置必须存在。它照规格做了、如实报 FAIL，**没有偷偷改测试让它绿**。
3. **反馈不成立**：我说某个按钮没反应，它查了代码说按钮和接口都在。**是我记错了。**

**别因为「我是下需求的人」就觉得它对不了。**
